# Rust 内置插件系统

插件编译进应用，通过服务契约互相协作，运行时可以启动、停止、卸载和替换实例。这里的插件与 Tauri 插件分别管理；不负责加载外部动态库。

## 角色与接口

- `PluginCreator` 声明插件 ID、提供的服务和必需依赖，并创建实例。构造函数只保存上下文和初始状态，不启动监听或分配平台资源。
- `Plugin: Send + Sync` 在 `start` 中创建资源，在 `stop` 中清理。原生对象仍由所属平台线程管理。
- `PluginContext` 提交本插件服务、获取已声明依赖、创建停止信号及登记异步任务。
- `PluginRegistry` 校验依赖图并协调生命周期；`services()` 返回只读服务访问入口。

创建 `PluginRegistry::new()` 后，先 `register::<T>()` 注册全部插件，再在 Tokio runtime 中调用 `start(id).await`。允许先注册消费者、后注册提供者。

`register` 为同步接口，生命周期队列忙时返回错误，不等待。其他生命周期接口为异步接口，串行执行。`state(&id)` 可查询状态和失败信息。插件回调执行时不持有注册表锁，但回调不能等待同一个管理器的生命周期操作，否则会相互等待。

## 服务契约

`PluginInfo.provide` 是插件必须在每次启动中提交的服务；`dependencies` 是启动前必须就绪的服务。每个 ID 只允许一个提供者，重复声明或重复提供者在注册时拒绝。缺失依赖、自依赖和循环依赖在启动前检查，失败时不会启动图中的任何插件。

在 `start` 中调用 `ctx.provide(id, service)`。服务先暂存，只有 `start` 成功且所有声明服务均已提交后，才在同一个写锁内统一发布。暂存期间外部无法获取；启动失败会全部撤销并调用 `stop` 清理。

消费者通过 `ctx.get_service::<T>(&id)` 获取 `Arc<T>`。上下文只允许访问声明过的依赖；宿主可以通过 `registry.services().get_service::<T>(&id)` 访问已发布服务。错误区分未就绪、类型不匹配、未声明和不允许的阶段。

类型擦除要求提交和获取使用完全相同的 `T`。建议每种服务在契约模块中集中定义 ID、trait 和获取包装。例如提交 `Box<dyn Screencast>` 后，必须获取 `Box<dyn Screencast>`，不能获取具体的 `PipeWireScreencast`。

服务表使用 `RwLock<HashMap<...>>`，使多服务发布与撤销具有统一的可见边界；获取时只克隆 `Arc`，调用服务期间不持锁。

撤销只阻止后续获取，不能收回已经交付的 `Arc`。有资源的服务应共享自身的运行状态，停止后拒绝新工作并让旧句柄返回明确错误。上下文访问规则用于约束协作，不提供进程内安全隔离。

## 生命周期与失败处理

状态包括 `Registered`、`Starting`、`Running`、`Stopping`、`Failed`。`Registered` 也表示已停止且清理完成，允许再次启动。失败状态包含阶段、错误信息以及是否仍需清理。

- `start` 按依赖顺序自动启动提供者。对已运行插件重复调用不会重新启动。
- 启动失败会先清理失败插件，再逆序回滚本次新启动的依赖。原本已运行的插件保持运行。若清理失败，其依赖会继续保留，错误中列出未完成的回滚。
- `stop` 会先发送停止信号、撤销服务，再调用停止钩子并等待登记的任务。已停止且清理完成时重复调用直接成功。
- 活动消费者，包括仍需清理的失败消费者，会阻止提供者停止、卸载或替换。停止消费者后，提供者保持运行，直到显式停止或关闭。
- `stop` 失败会保留实例和待清理状态，可以再次调用；清理完成前禁止重新启动。
- `uninstall` 仅在停止成功后删除实例。
- `replace_plugin::<T>` 要求相同 ID 的旧实例已停止且清理完成。声明检查或新实例构造失败保留旧实例，成功替换后仍为 `Registered`。
- `shutdown` 按消费者优先的顺序停止所有活动插件，失败时保留实例供重试；它不卸载插件或永久关闭管理器。

异步生命周期操作第一次被轮询并提交后，由管理器独立任务执行。丢弃调用方的 future 不会中断收尾；该保证依赖 Tokio runtime 继续运行。宿主退出前必须显式等待 `shutdown`，不能依赖 `Drop` 完成异步资源清理。当前框架尚未接入 Tauri 退出流程。

启动和停止钩子的 unwind panic 会被转为失败并尝试清理；这不构成完整故障隔离，进程 abort 无法恢复。

## 后台任务与平台资源

每次启动创建独立的停止信号。先通过 `ctx.stop_signal()` 获取信号，再登记任务：

```rust,ignore
let mut stop = ctx.stop_signal()?;
ctx.spawn(async move {
  loop {
    tokio::select! {
      _ = stop.cancelled() => break,
      event = receiver.recv() => {
        // 处理事件；关闭时退出，错误按业务语义返回。
      }
    }
  }
  Ok(())
})?;
```

停止时，登记的任务共享 5 秒协作退出期限；超时任务会被 abort 并等待结束，同时记录停止失败。任务错误和 panic 会在收尾时报告，目前不会自动触发插件停止。任务必须及时让出执行权，阻塞线程或无法取消的原生操作不能依赖 async abort 清理。

插件的 `stop` 钩子必须支持启动到一半时调用以及清理失败后的重试。钩子本身没有强制超时，应自行保证平台清理能够结束；卡住的钩子会阻塞生命周期队列。通过 Context 登记的任务由管理器等待；平台线程、未登记的任务和捕获会话仍由插件停止钩子明确关闭。

`platform` 模块独立实现底层捕获能力，插件只负责包装、发布服务和资源归属。当前插件框架尚未接入 RGB 告警业务，也未据此完成屏幕捕获授权或实际采集验证。
